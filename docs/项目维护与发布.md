# 项目维护与发布

仓库维护一份核心源码，Release 保存各平台可安装的产物。当前版本号见根目录 `VERSION`；Codex 包内的版本由构建脚本从该文件生成；Claude Code、WorkBuddy 与 DSH 追加包从指定核心提交的 VERSION 读取版本。

## 日常改动

在现有主工作目录中修改对应 kit；有多项并行工作时使用短期功能分支。四个 kit 的接口与样例随代码一起维护。平台入口、清单和运行约定放在 `adapters/<平台>/`，避免复制后再分别修改计算代码。

改动完成后运行相关测试；涉及模块交接或发版时运行全部测试。测试使用人工样本，GitHub Actions 不配置数据密钥、不调用 iFinD 或真实行情接口。

本机验证（临时文件保存在既定位置）：

```bash
mkdir -p /Users/ranli/Documents/Codex/temp/multi-asset-tests
export TMPDIR=/Users/ranli/Documents/Codex/temp/multi-asset-tests
export QUANT_REPORT_TEST_TMP="$TMPDIR"
python -m unittest discover -s quant-data-kit/tests -q
python -m unittest discover -s quant-strategy-kit/tests -q
python -m unittest discover -s quant-report-kit/tests -q
python -m unittest discover -s quant-rebalance-kit/tests -q
python -m unittest discover -s tests -q
```

其他电脑使用自己的临时目录。提交前检查文件列表，确保只有代码、配置样例、模板和文档。根目录 `.gitignore` 排除本地 `output/`、`资料/`、根目录 `references/`、研究材料、环境、行情文件和凭证；各 kit 内的 `references/` 是使用说明，会进入仓库。

方案与申报文件集中在 `资料/`，每轮运行结果完整放在 `output/验证与测试/<批次>/`。当前可看的报告由该目录的 README 提供入口；旧交付快照放在 `output/历史交付/`。历史报告内的来源路径记录生成时的位置，迁移后的对应位置见本地整理记录。

## Codex 发版

1. 更新 `VERSION`，完成测试并提交源码。后续同一版本的安装包应对应同一提交；有修订则使用新版本号。
2. 试构建先放到 `/Users/ranli/Documents/Codex/temp` 下的任务目录。正式构建从干净的源码工作区生成，输出使用新版本目录：

   ```bash
   python scripts/build_codex_release.py --out output/releases/v0.1.0
   ```

3. 将生成的 ZIP 解压到另一个目录，检查 `startup`、策略配置及数据计划，并在 Codex 插件目录验证识别。首次启用使用人工样本，不必消耗真实数据额度。
4. 为通过验证的提交建立 `v0.1.0` 标签并推送，创建同名 Release，上传 `multi-asset-investment-codex-v0.1.0.zip` 和 `SHA256SUMS`。发布说明写明新增内容、下载文件和安装入口。
5. 其他宿主的安装包可以追加到对应核心版本的 Release；若核心也改动，整体发布新版本。适配源码始终进入仓库。

GitHub 自动生成的 Source code 下载项保留源码结构；提供给 Codex 用户的文件是命名中带 `codex` 的 ZIP。Release 不打包真实研究结果。

## WorkBuddy 追加发行

适配层在 `adapters/workbuddy/`，同样复用核心标签的四个模块和统一 Skill，产物是 WorkBuddy 的本地插件市场。先提交适配源码，再运行：

```bash
python scripts/build_workbuddy_release.py --core-ref v0.1.0 --out output/releases/v0.1.0/workbuddy
```

包内结构是市场根目录加 `plugins/multi-asset-investment/`，市场清单与插件清单共用同一版本号，插件目录必须位于市场根目录之内。市场名称固定为 `multi-asset-investment-local`；安装时在 WorkBuddy 插件面板添加市场，市场源填解压目录的完整路径，不需要命令行。将生成的 `multi-asset-investment-workbuddy-v0.1.0.zip` 和 `SHA256SUMS-workbuddy.txt` 追加到已有 v0.1.0 Release，保留原 Codex 附件、校验文件与标签。

首次适配的自动检查在 `tests/test_workbuddy_bundle.py`：解压到含空格的路径后核对市场清单与插件清单一致、逐文件哈希、以及 `startup` 与策略配置的离线运行。WorkBuddy 客户端内的添加市场、安装与端到端对话尚未执行，以使用者本机界面结果为准；发布说明只写功能与安装方法，验证过程留在内部维护资料。

## DSH 追加发行

适配层在 `adapters/dsh/`，同样复用核心标签的四个模块和统一 Skill，产物是 DeepSeek Harness（DSH）的组合包。先提交适配源码，再运行：

```bash
python scripts/build_dsh_release.py --core-ref v0.1.0 --out output/releases/v0.1.0/dsh
```

包内结构是安装目录 `multi-asset-investment-dsh/` 加同名 ZIP。`package.json` 声明组合入口 `dsh.bundle.patch`，`cordis.patch.yml` 登记一行插件（行名即包名），`index.js` 是宿主插件入口，把包内 `skills/multi-asset-investment` 注册到会话技能目录并给出技能基准目录；组合包不额外声明 npm 依赖，技能注册使用 DSH 提供的宿主接口。安装时在侧栏「插件」页点「添加插件」，填入解压目录的完整路径；也可以让 Agent 用插件管理安装该本地目录。将生成的 `multi-asset-investment-dsh-v0.1.0.zip` 和 `SHA256SUMS-dsh.txt` 追加到已有 v0.1.0 Release，保留原 Codex 附件、校验文件与标签。

不使用插件时，DSH 会扫描技能目录：把包内 `skills/multi-asset-investment` 复制到 `~/.dsh/skills/`（用户级）或项目的 `.dsh/skills/`（项目级）即可被识别，无需重启。

自动检查在 `tests/test_dsh_bundle.py`：解压到含空格的路径后核对组合入口与插件行、逐文件哈希、`startup` 与策略配置的离线运行，并用 Node 加载 `index.js` 确认只注册一个 Skill、名称与技能基准目录正确（未安装 Node 时跳过该项）。DSH 客户端内的插件安装与端到端对话尚未执行，以使用者本机结果为准；发布说明只写功能与安装方法。
